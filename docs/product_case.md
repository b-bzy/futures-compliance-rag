## 一、项目背景

期货行业是强监管行业，法规、交易所规则与内部制度更新频繁。业务与风控人员在实际作业中遇到的问题往往是「这笔业务对应哪一条规定、最新版本怎么说」——传统做法是翻 PDF、问合规同事，耗时且容易引用到过期版本。

同时，合规文件本身高度敏感，**不能出公司网络**，这直接决定了架构必须是本地化部署，而非调用外部大模型 API。

## 二、我的角色与职责

负责该合规 AI 助手的产品设计与落地推动。

### 1. 文档入库链路

- **PDF 文件 OCR 识别**：法规文件大量以扫描件、图文混排 PDF 形式存在，需先做 OCR 才能进入检索链路
- **语义切分入库**：按条款语义边界切分而非固定字数切分，保证一个条款不被拦腰截断

### 2. 检索链路

- **混合召回**：结合关键词检索与向量语义检索，兼顾「精确条款号命中」与「模糊业务描述命中」两类查询
- **重排序（rerank）**：对混合召回的候选做二次排序，提升 Top-K 结果的准确率

### 3. 交互形态

- 提供**对话式合规条款即时查询**，用户用业务语言提问，助手返回条款原文与出处

## 三、关键设计取舍

- **为什么必须本地化部署**：合规文件涉密，不可上传外部 API，这是架构的第一约束而非优化项
- **为什么做混合召回而非纯向量**：合规查询里既有「《期货交易管理条例》第几条」这类需要精确匹配的，也有「客户适当性怎么做」这类语义查询，单一召回方式必有一类失准
- **为什么按语义而非定长切分**：法规的最小语义单元是「条」，切碎条款会让召回结果失去可引用性
- **为什么必须给出处**：合规场景下，一个没有条款出处的答案是不可用的——用户需要能回溯原文自行确认

## 四、成果

- 交付基于本地化 RAG 架构的合规 AI 助手，全链路数据不出内网
- 打通 OCR → 语义切分 → 入库 → 混合召回 → 重排序 → 对话式问答的完整链路
- 解决法规更新频繁场景下的条款即时查询问题

## 六、这些设计取舍，我自己实现了一遍

上面四条取舍在本仓库的代码里都有对应的落地与实测，可直接对照：

| 本文档里的取舍 | 代码/实测位置 |
|---|---|
| 混合召回优于纯向量 | 三路召回 [`retrieve/hybrid.py`](../src/derivrag/retrieve/hybrid.py)；消融实测**混合后反而比纯向量差 10.7 pp**，直到改用 score-aware 融合才恢复 —— 见 [RESULTS.md](../eval/reports/RESULTS.md) |
| 融合策略 | 自研 score-aware RRF [`retrieve/fusion.py`](../src/derivrag/retrieve/fusion.py)，相对标准 RRF +12.0 pp |
| 重排序提升 Top-K | 交叉编码器 [`retrieve/rerank.py`](../src/derivrag/retrieve/rerank.py)，Recall@1 +6.7 pp，延迟 0.10s → 4.53s |
| 按条款语义切分 | 条款级父子分块 [`chunk/clause.py`](../src/derivrag/chunk/clause.py) |
| OCR | [`parse/pdf.py`](../src/derivrag/parse/pdf.py)；实测 190 份文档里**只有 6 页真正需要 OCR**，PaddleOCR 最终没用上，原因见 [decisions.md](decisions.md) |
| 必须给出处 | 强引用约束生成 [`llm/prompts.py`](../src/derivrag/llm/prompts.py)，引用精确到「某规则第 X 条」 |
