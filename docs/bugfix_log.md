## 1. 推理模型思考 token 吃满预算导致正文为空

### 现象

两个看起来无关的表现，其实同一个根因：

- 问「备兑开仓的保证金怎么算？」→ 召回 5 条引用，**答案是空字符串**，界面一个空气泡
- 开启 HyDE → 照常付费、照常等待 16 倍延迟，**假设文档是空的**，静默降级成不用 HyDE

### 诊断证据

直接抓 API 原始响应，不看封装后的结果：

```
问题：备兑开仓的保证金怎么算？   max_tokens=2048
finish_reason:      length
content 长度:        0
reasoning 长度:      3315
completion_tokens:  2048   其中 reasoning_tokens: 2048
```

`reasoning_tokens` 等于 `completion_tokens` 等于 `max_tokens` —— 思考阶段就撞上上限，
一个正文 token 都没轮到。HyDE 同理：

| `max_tokens` | `finish_reason` | reasoning | content |
|---|---|---|---|
| 256（原配置） | length | 256 | **0 字** |
| 2048 | stop | 216 | 195 字 |

### 根因

`deepseek-flash` 是推理模型，**思考 token 与正文共用 `max_tokens`**。调用方按
「这个任务输出很短」给小预算时，预算被思考烧光。

而 `provider.chat()` 当时是 `return content or ""` —— **完全不看 `finish_reason`**，
静默返回空串。调用方无从区分「模型没话说」和「被截断」。

仓库里一共四处这样的小预算：

| 位置 | 预算 | 静默失效的后果 |
|---|---|---|
| `query.hyde.max_tokens` | 256 | HyDE 白花钱 |
| `hyde.py` `rewrite_query` | 200 | 多轮改写失效，追问不被补全 |
| `04_mine_qa.py:253` | 512 | QA 挖掘产出空 |
| `04_mine_qa.py:365` | 200 | **去泄漏改写失效 → 评测集没去泄漏 → 消融数字全废** |

最后一条最危险：它等于复现 [audit.md](audit.md) 记录过的「六个消融档位全是
Recall@1 = 1.000」那场灾难，而且不会有任何报错。

另外 HyDE 的 `256` 同时存在于 `configs/config.yaml`、`hyde.py` 默认值、
`pipeline.py` 兜底默认**三处**，改一处另两处照样复活。

### 否决的方案：逐个调用点改数字

第一版就是这么改的（256→2048、200→1024）。**这是打地鼠**：四处小预算、三处
重复常量，而且治不住下一个新增的调用点。

### 采用的方案：三层

**第一层 —— provider 边界加输出预算下限（核心）**

`OpenAICompatProvider` 新增 `min_output_tokens`（默认 1024，配置项
`llm.min_output_tokens`，设 0 关闭）。`chat()` 与 `stream()` 都过 `_floor()`。

收益：`04_mine_qa.py` 那两处**一行没改**，自动被兜住。这是边界修法与打地鼠的
本质区别 —— 治的是整类问题。

告警只发一次（去泄漏改写会连着调 222 次，刷屏就没人看了）。

**第二层 —— 失败必须显式**

- 新增 `LLMTruncatedError(RuntimeError)`。继承 `RuntimeError` 是刻意的：
  `api/server.py` 已捕获它转 503，界面能看到明确原因而不是空白
- `chat()`：正文为空且 `finish_reason == "length"` 时，把预算提到 3 倍
  （上限 16384）重试一次；仍为空则抛错。非 `length` 说明不是预算问题，不浪费重试
- `stream()`：流式已在推事件，不能重试。改为记录是否产出过正文，一个都没有就抛错，
  让 SSE 层发 `error` 事件

**第三层 —— 降级要响亮、要可观测**

- `generate_hypothetical` 原先用 `except Exception` 把所有失败混为一谈（还会把新加的
  `LLMTruncatedError` 一起吞掉）。改为按原因分级：**预算不足记 ERROR**（配置错误，
  必须有人看见）、**网络/限流记 WARNING**（运行时波动）。混同会让告警失去区分度
- `pipeline` 在「请求了 HyDE 但一份文档都没拿到」时记 `timings["hyde_ineffective"]`
  并打 ERROR。否则消融实验会把 `plus_hyde` 档测成 `plus_rerank` 档，
  得出的「HyDE 无收益」是自证预言

### 验证

- 单元测试 15 例（stub，不联网）：见 [bugfix_testcases.md](bugfix_testcases.md#缺陷-1-的用例)
- 真实 API：同一问题现在返回 783 字带 5 条引用的答案，并如实说明确切公式不在语料里
- HyDE 现在产出 195 字假设条款，`hyde_ineffective` 未触发
- 健壮性探针 G2（空答案回归）从 FAIL 转 PASS

### 遗留

**`eval/reports/ablation_hyde50.md` 那张表可信度存疑。** 它是在
`max_tokens=256` 下跑的，假设文档很可能是空的 —— 也就是说「HyDE 与不开完全打平」
测的其实是「不开 HyDE vs 不开 HyDE」，打平是必然的。要确认只能重跑（50 条约 0.08 元）。

## 2. 关键词通路无法定位到具体文档

### 现象

问「《上海证券交易所股票期权试点交易规则》第十二条规定了什么？」，系统答
**「根据现有条款无法确定」** —— 拒答本身是诚实的，但那一条明明在索引里。

### 诊断证据

分四步排除，每步都缩小范围：

**第一步：文档在语料里吗？** 在。

```
sse_rule_..._的通知       正文   498 字
sse_rule_..._的通知_att0  正文 22085 字   ← 规则全文在附件里
```

> 这一步我判断错过一次：脚本取了 `hit[0]`，那是 498 字的**通知正文**（4 个父块
> 完全正常），我据此报告「切分器把 162 条丢了 158 条」。**是错的。** 取到附件后
> 确认 `第十二条` 到 `第一百七十一条` 全在 `parents.jsonl` 里，切分没问题。
> 教训：同一份文件的通知与附件是两条独立记录，按标题匹配会同时命中，别取 `[0]`。

**第二步：那一条进索引了吗？** 进了。

```
parents.jsonl 里含该条原文的父块: 1 个
doc_id=sse_rule_..._att0  clause_id='第十二条'
```

**第三步：关键词通路能查到它吗？** 查不到。

```
库里 clause_id='第十二条' 的块: 59 个，分布在几十份规则里
_keyword 构造的 where: {"clause_id": "第十二条"}    ← 没有文档维度
目标文档那一条是否在返回集里: 不在
加上文档维度后: {"$and":[{"clause_id":"第十二条"},{"doc_id":target}]} → 精确返回 1 条 ✓
```

**第四步：通路修好后就够了吗？不够。** 修好后 `_keyword` 确实返回了正确那一条，
但 `channel_counts` 里**依然没有 keyword** —— 它在融合阶段被挤掉了。算一下融合
得分上限：

| 通路 | 权重 | 单路命中的得分上限（`score_weight=0.3`, `k=60`） |
|---|---|---|
| dense | 0.50 | 0.7·(0.50/61) + 0.3·0.50 = **0.1557** |
| bm25 | 0.30 | **0.0934** |
| **keyword** | **0.20** | 0.7·(0.20/61) + 0.3·0.20 = **0.0623** |

keyword 单路命中的**上限**低于 dense 的**上限**。也就是说只被 keyword 命中的块
**无论多准都进不了 top-5**。这不是调参问题，是结构性的。

而 `hybrid.py` 开头的注释写的正是「能直接按 clause_id + doc_title 精确定位」——
权重设置否决了这个设计意图。

### 根因

两个独立成因叠加：

1. `_keyword` 只按 `clause_id` 查，**不用查询里的《规则名》**。59 个同名条号按
   `limit` 截断等于随机取几个
2. 即使通路返回了正确那一条，融合的加权投票机制让它必然落选

### 否决的方案

**调高 keyword 权重** —— 会连带抬高那些「同名条号但不知道是哪份文件」的弱匹配
（不带规则名时通路会返回 20 条无关文档的同名条款），整体质量下降。

**给 keyword 通路内部做分数区分** —— 融合里的 `_min_max_normalize` 是**通路内**
归一化，若通路只返回精确匹配，它们会被归一到全 1.0，区分度消失。没用。

### 采用的方案

**文档维度约束**：新增 `_DOC_TITLE_REF` 提取《…》（少于 4 字的不要，`《说明》`
这类短词多半不是文件名），用 `_title_index`（懒加载，从已在内存的父块存储建，
190 个文档零额外 IO）反查 `doc_id`，再用 `{"$and":[..., {"doc_id":{"$in":[...]}}]}`
约束。

用**子串双向包含**而非相等：库里 `doc_title` 往往是「关于发布《X》的通知（附件）」，
用户只写《X》，两者永远不相等。

文号 `doc_no` 本身就是文档唯一标识，不需要书名号也算「点名了文档」。

**精确匹配不参与投票**（`_pin_exact`）：用户写「《X规则》第十二条」时，他不是在
描述一个检索意图让各路去投票，而是在**指定一条确定的记录**。这种匹配置顶，
保证不被融合或重排挤掉。

只在「点名了文档（书名号或文号）+ 命中条号/文号」时触发，范围极窄。置顶数量有
上限 `retrieve.max_pinned_exact: 2` —— 一个文号最多覆盖 117 个块（实测），
只给文号不给条号时全部置顶会挤爆 `top_k`。

点名的文件里确实没有那一条时，退回全库查同名条号（好过什么都不返回），
但**不标记为精确匹配**。

### 验证

- 单元测试 13 例（stub，不加载模型）：见 [bugfix_testcases.md](bugfix_testcases.md#缺陷-2-的用例)
- 真实端到端：

```
INFO 精确匹配置顶 1 条（融合/重排未保留它们）: ['第十二条']
三路命中: {'keyword': 1, 'exact': 1, 'dense': 4, 'bm25': 4}

答案：第十二条规定的是合约标的除权、除息时，本所对相关期权合约的合约单位、
      行权价格进行调整，并重新挂牌新的期权合约。
引用 [1] 关于发布《上海证券交易所股票期权试点交易规则》的通知（附件） | 第十二条
```

- 健壮性探针 C2/C3 从 FAIL 转 PASS，全量 **37/37 零缺陷**

## 3. 附带修正

这几条不是独立排查出来的，是做别的事时撞上的，一并记下。

### 3.1 文号抽取率 26% 被误判为抽取缺陷

`audit.md` §2.2 原本断言「`extract_doc_no` 只认一种全角样式，实际还有
`第 48 号`、英文 `Circular No.` 等变体」，并承诺「覆盖率 26%→80%+」。

实测推翻：那些变体在语料里命中数**全是 0**；把扫描窗口从 3000 字符放大到全文
只多 1 份；140 份缺文号的文档里 **0 份**在原始文件里有文号可捞（含中金所 25 份
「通知」类，原始 HTML 里 0/25 有文号）。

**26% 是语料属性，不是抽取缺陷**：缺文号的是合约条款表、常设规则手册、投资者
问答与英文 rulebook，本身不带发文字号，返回 `None` 是正确行为。对照组印证：
CFFEX 抽到文号的 14 份**全部**是「关于……的通知」。

修了正则里真实存在的那 1 份（机构前缀改可选），并**没有**添加 0 命中的变体分支
—— 那正是 audit §1.2 自己批判的「装饰品」。真实天花板改写为 39%。

> 顺带修了自己引入的缺陷：前缀改可选后「上证发 〔2023〕48号」会退化成部分匹配、
> 静默返回「〔2023〕48号」，把机构简称吞掉 —— 机构简称是引用真值的一部分，
> 丢了比返回 `None` 更糟。加了 `\s*`。

### 3.2 httpx 缺 `[socks]` extra 导致 LLM provider 静默判定不可用

`ALL_PROXY=socks5://...` 存在时，httpx 在**构造 client 时**就要求 `socksio`，
缺了会 ImportError。表现极具误导性：报「没有可用的 provider，请配 API key」，
而 key 其实是对的；`huggingface_hub` 下模型同样在构造 client 时炸。

**用 curl / urllib 测同一个 key 完全正常**（它们走系统代理、不经 httpx），
于是很容易误判成「密钥已验证可用」—— 我就误判了一次。

修法：`requirements.txt` 的 `httpx` 改为 `httpx[socks]`。

> 同一台机器上还有一个相关现象：`huggingface_hub` 的 Xet 后端走该代理不通
> （80 秒 0 进度），`HF_HUB_DISABLE_XET=1` 退回经典 HTTP 路径后速率从
> 575 KB/s 跳到 1570 KB/s。

### 3.3 manifest 的 `local_path` 存绝对路径，`data/` 一搬就全失效

`Fetcher` 写入时 `cfg.resolve` 会无条件转绝对路径（`config.py` 的 `resolve`
是 `return p if p.is_absolute() else repo_root() / p`）。`data/` 一旦搬动，
`02_parse.py:135` 的 `Path(rec["local_path"])` 会对**每一份**文档失败。

修法在读取侧：按仓库根目录还原相对路径，绝对路径失效时再按文件名回退到当前
`raw` 目录。三种情形（相对 / 绝对指向旧目录 / 绝对指向新目录）均已验证可解析。
读取侧修比写入侧修更稳 —— 不依赖 manifest 里存的是什么。

### 3.4 语料份数 191 → 190

`manifest.jsonl` 有 191 条记录但只对应 **190 个唯一 doc_id**：中金所《关于调整
股指期货手续费标准的通知》被记了两次（一次 `status=ok`、一次 `status=skipped`，
同一文件同为 33,419 字节，第二次命中本地缓存未重下）。抓取器按每次 fetch 尝试
追加记录，**manifest 行数 ≠ 文档数**。

三处独立口径都是 190：`data/raw` 下实际文档文件 190 个、`stats.json` 的
`documents_fetched`/`documents_parsed` 均为 190、`parents.jsonl` 唯一 `doc_id` 190。
`corpus.md` 里按交易所的明细合计本来也是 190，与表头的 191 自相矛盾。

已改 8 处表述。5,365 父块 / 14,710 子块 / 331 万字 逐项核对无误，未动。
